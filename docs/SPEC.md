## 1. 概要と今回の範囲

### ゲームの概要

机ひとつでPCを組み始め、人を雇い、他社と契約・買収しながら世界的なPCメーカーに育てる経営シミュレーション。タイクーンゲームの「効率が一気に上がる」手応えと、incゲームの「画面に物があふれていく」気持ちよさを掛け合わせる。スマホの縦画面で遊ぶブラウザゲーム。

### 試作1で作る範囲：段階1（自室）

開始から、所持金が 400,000円（貸し倉庫の初期費用）に届いてクリアするまで。想定の遊び方で約5分。

作るもの
- 3つの列（生産・制作・販売）の画面と、行き来するための切り替えバー
- 自分の手での作業（分解・組み立て・発送）
- ジャンクPCの仕入れ（手動と自動）
- フリマの注文（時間切れで逃す）
- アルバイトの雇用（段階1は2人まで）
- 下請けの依頼（受ける・納期・違約金）
- 60秒ごとの支払い、払えないときの猶予と倒産
- 段階1のクリア画面、倒産画面
- オートセーブと、閉じていた間の進行（最大2時間）
- 昼と夜の配色

作らないもの（試作2以降）
- 段階2以降（貸し倉庫・工場など）、部屋の強化
- 下請け以外の契約（仕入れ・外注・卸）、買収、ライバル企業、市場の出来事
- 周回（創業者の得意分野・町・スコア・持ち越し）
- 事務用PC・ゲーミングPCなど再生PC以外の製品（鍵付きで表示だけする）
- 音、PWA、部屋のズームやスクロール

試作1で確かめたいこと
- 手作業が忙しく、客（注文）を逃す「最初の苦労」があるか
- アルバイトを雇った瞬間に、楽になって収入が一気に伸びる手応えがあるか
- 部品や完成品が画面にあふれる見た目になっているか
- スマホ縦画面・片手で遊べるか
- 画面を行き来しても、詰まっている列に気づけるか

基準サイズは 390×844（CSSピクセル）。端末の幅に合わせて拡大縮小し、縦長の端末では上下に余白を足す。

- 販売：完成品 − 1
待っている注文の数は判定に使わない（注文がたまるのは作る側が遅いときの症状で、販売の列の遅れではないため）。ラフの「！」の位置は例で、実際の表示はこの式に従う。見た目の目安なので、試作中に調整してよい。

- パネル「フリマの注文」：待っている注文の一覧（残り時間の輪・品名・価格・残り秒数。残りが少ない注文は赤）、逃した注文の数（×n）、下請けの依頼が来ていればその行と「受ける」ボタン
- 作業ボタン：発送
- 売れた瞬間に部屋の上へ「+¥16,320」を飛び出させる

### 経営タブ

- 社員：アルバイトを雇うシート（docs/rough/04_hire_sheet.png。背景は古い版のラフなので、シートの中身だけ参考にする）
  - 雇用費・給料（60秒ごと）・速さの3つのタイル
  - 担当する列の選択（生産・制作・販売）。今いちばん詰まっている列に赤い数字を付ける

  - 支払いの確認：雇ったあとの手元が次の支払い額以上なら「支払いOK」、足りなければ警告
  - 「¥60,000で雇う」ボタン（所持金が足りなければ押せない）
  - 雇っている人の一覧（担当列の変更ができる）
- 契約：下請けの依頼と、受けている下請けの状況
- 買収：鍵（段階4で解放）
- 財務：直近の支払いの区切りごとの売上・費用・利益（数字の表でよい）

### そのほかの画面

- 段階1クリア：所持金が 400,000円に届いたら「貸し倉庫へ移る」ボタンを出し、押すとクリア画面（クリアまでの時間、売った台数、雇った人数）。試作1はここで終わり

## 3. ルール

### 物の流れ

ジャンクPC →（分解）→ 部品 →（組み立て：部品4個）→ 完成品PC →（発送：注文1件）→ 入金

### 作業の仕組み

- 作業は1回ずつ行う。始める時点で材料を取る（同じ材料を2人が使わないため）
  - 分解：ジャンク1台 → 完了時に部品を1〜4個（確率は balance）
  - 組み立て：部品4個 → 完了時に完成品1台。下請けを受けていて「下請けを優先」がONなら、支給キット1つ → 完了時に下請け1台分を納め、報酬を受け取る
  - 発送：完成品1台と待っている注文1件 → 完了時に 売値×(1−手数料率)−送料（16,320円）を入金
- 自分の手：今いる画面の列の作業だけできる。作業ボタンをタップすると1回、長押しすると材料がある限り続ける。作業中に画面を移ると、その作業は完了まで進み、次は始めない
- アルバイト：担当の列で材料がある限り自動で作業し続ける。速さは自分の0.9倍（作業時間 ÷ 0.9）。同じ列に自分とアルバイトがいれば両方が並行して作業する
- 制作のアルバイトは、「下請けを優先」がOFFでも、通常の部品がなく支給キットがあればキットを使う

### 仕入れ

- 手動：×1・×5 ボタン。所持金が足りる分だけ買う
- 自動仕入れ（最初からON）：次の条件をすべて満たすとき、1台ずつ買う
  - ジャンク在庫が keepJunk（2台）未満
  - 部品が pauseWhenPartsAtLeast（12個）未満、完成品が pauseWhenPcsAtLeast（3台）未満
  - 買ったあとの所持金が、次の支払い額（電気代＋給料×人数）以上
- ただし、ジャンク・部品（4個以上）・完成品がすべてなく作業が止まっているときは、支払い額の取り置きを崩してでも1台買う

### 注文

- 届き方：平均間隔の指数分布（ポアソン到着）。1秒あたりの到着率 = min(maxMultiplier, 1 + growthPerSale × 売った台数) ÷ baseIntervalSeconds
- 待ち時間：届いてから patienceSeconds（15秒）以内に発送が始まらないと失われる（ほかの出品者から買われた扱い。逃した数を数える）
- 発送は古い注文から順に当てる

### 支払い

- intervalSeconds（60秒）ごとに、電気代1,500円＋給料12,000円×アルバイトの人数を払う
- 払った結果、所持金がマイナスなら graceSeconds（30秒）の猶予に入る。猶予中に0以上に戻れば解除。戻らなければ倒産
- 銀行からの借り入れはない

### アルバイト

- 雇用費60,000円、給料は支払いのたびに1人12,000円、段階1では2人まで
- 雇うときに担当の列を選ぶ。あとから変えられる

### 下請け

- 開始から firstOfferAtSeconds（45秒）後に最初の依頼、その後 offerEverySeconds（75秒）ごとに依頼が来る（受けている下請けがあるときは来ない）
- 依頼は offerExpiresSeconds（20秒）以内に「受ける」を押すと成立する（この20秒は仮の決め。シミュレーションでは依頼が来た瞬間に受けている）
- 受けると支給キットが units（6台分）届き、deadlineSeconds（90秒）の納期が始まる
- 1台納めるごとに feePerUnit（4,000円）が入る。全部納めれば完了
- 納期までに残った台数 × penaltyPerUnit（4,000円）の違約金を払って終わる

### 段階1のクリアと倒産

- 所持金が clearCash（400,000円）以上になったら「貸し倉庫へ移る」を出す。押したらクリア（試作1の終わり）
- 倒産したら倒産画面から最初に戻る

### 時間の進め方と乱数

- ルール本体は tickSeconds（0.1秒）刻みで進める。画面の描画とは切り離す
- 乱数は種つきの疑似乱数（例：mulberry32）を使う。使う箇所は、分解で取れる部品の数と、注文の到着間隔の2つだけ
- ゲーム内の日付や時刻は持たない。表示はすべて「あと◯秒」
- テストのために、URL の ?seed=数字 で乱数の種を固定し、?speed=倍率 で時間の進みを速められるようにする

### 命令（画面からルール本体へ渡すもの）

- workTap(列) / workHold(列, 押している)
- setScreen(列)（今いる画面＝自分の手がある列）
- buyJunk(台数) / setAutoBuy(ON/OFF)
- hire(列) / reassignWorker(番号, 列)
- acceptSubcontract() / setSubcontractPriority(ON/OFF)
- moveToWarehouse()（クリア）
- restart()

### 閉じていた間の進行

- 最後に保存した時刻との差（最大 offlineMaxSeconds＝2時間）を、ルール本体の同じ刻みでまとめて進める
- 不在中は自分の手は動かない。アルバイト・自動仕入れ・注文・支払い・下請けの納期は進む
- 不在中は倒産させない。支払えないときはアルバイトを休ませ（作業も給料も止める）、戻ったときのまとめで知らせる。戻ったら休みを解く

## 5. 手触りの目安（テストで確かめる）

docs/sim_stage1.py の Smart（想定の遊び方）をTypeScriptのテスト用ボットとして移植し、ルール本体で種を変えて100回動かした中央値で確かめる。ボットは長押し相当（材料があれば休まず作業する）で動き、作業のたびに画面を自由に移る（移るのにかかる時間は0）。下請けは来た瞬間に受ける。

| 指標 | 目安 | シミュレーションの値 |
|---|---|---|
| 初めて売れるまで | 8〜15秒 | 10.5秒 |
| 初めて雇うまで | 60〜100秒 | 70秒 |
| 注文の取りこぼし | 雇う前 10〜35%、雇った後120秒は雇う前の半分以下 | 33% → 14% |
| 雇う前後の収入の伸び（雇う前30秒と雇った後5〜65秒の1秒あたり収入の比） | 1.6倍以上 | 1.72倍 |
| クリアまで | 240〜360秒 | 288秒 |
| 倒産 | 0% | 0% |
| 下請けを受けないボットとの差 | クリアが5〜20%遅い | 9%遅い |
| 状況を見ない対照ボット（生産→制作→販売を順番に回す） | 想定の遊び方より大きく遅い | 15分でクリアできない |

Smart ボットの要点（詳しくは docs/sim_stage1.py の Smart クラス）
- 手の使い方：発送できるなら発送 → 下請けの納期が迫っていれば下請けの組み立て → 完成品が3台未満なら組み立て → 部品が8個未満なら分解 → それ以外も材料があるものを進める
- 雇う条件：所持金が 雇用費＋次の支払い額（電気代＋給料×雇ったあとの人数）＋ジャンク1台分 以上。1人目は制作、2人目は生産を担当。2人目は組み立ての速さが注文に追いついていないときだけ雇う
- 仕入れ：自動仕入れと同じ条件

仕様の細部（依頼の有効時間など）がシミュレーションと違うため、数値が少しずれるのは構わない。目安から外れたときは、balance.json を勝手に変えず、どの指標がどれだけ外れたかを報告する。

## 6. セーブ

- 保存先：localStorage。保存の窓口（SaveStore）を1つにまとめ、あとで IndexedDB（Dexie）に差し替えられるようにする
- 版番号：saveVersion = 1。古い版のセーブを新しい版へ変換する関数を用意する（試作1では変換対象なし）
- 保存する項目：ルール本体の状態すべて（所持金、在庫、部品、完成品、注文、作業中の作業と残り時間、アルバイト、下請け、次の支払いまでの時間、猶予、統計、乱数の状態）、最後に保存した時刻、今いる画面、設定
- 保存のタイミング：5秒ごと、画面が隠れたとき（visibilitychange）、雇う・受ける・クリアなどの大事な命令のあと
- セーブの書き出し・読み込み：設定画面で、セーブをテキストとして書き出し、貼り付けて読み込める

## 7. 操作

- 作業ボタン：タップで1回、長押しで連続。押している間は進み具合の輪が回る
- 画面の切り替え：切り替えバーのボタンをタップ、または画面全体を左右にスワイプ（スワイプは画面全体を包む要素で受け取り、部屋のcanvasに取られないようにする）
- 経営タブ：タップで下からシートを開く。下へスワイプか×で閉じる
- 押せる物はすべて44px以上
- 部屋は見るだけ（試作1ではズームやスクロールはしない）

## 8. 見た目の決まり

- 書体は1つだけ：M PLUS Rounded 1c（Google Fonts、400・700・800）
- 文字を減らす：状況はアイコン・数字・物の量で伝える。説明の文章は画面に置かない
- 物は数だけ描く：ジャンク・部品・完成品・箱は実際の数だけ部屋に描く（多くなったら積み上げる。まとめ表示は試作2以降）
- 詰まっている列は、切り替えバーの「！」に加えて、その部屋の床の縁を列の色で光らせる
- 部屋の描き方：線を使わないフラットなアイソメトリック。影は一段暗い色の面で表す。部屋は背景に浮かぶ一枚の台のように描く（docs/rough の画像に合わせる）
- 昼と夜：端末のダークモード設定に合わせ、設定で切り替えられる。夜は窓・モニター・ドアが明るく光る

配色（役割ごとに分ける）

| 役割 | 昼 | 夜 |
|---|---|---|

## 10. 完了の条件

1. npm test（Vitest）がすべて通る
   - 同じ種なら同じ結果になる
   - 閉じていた間をまとめて計算した結果が、同じ時間を実際に進めた結果と一致する（自分の手を動かさない条件で）
   - セーブして読み込んでも状態が変わらない
   - balance.stage1.json が Zod の検査を通る
   - 5章の手触りの目安（ボット100回の中央値）
2. npm run e2e（Playwright、390×844）がすべて通る
   - 開いて3つの画面を切り替えられる（タップとスワイプ）
   - 作業ボタンで分解・組み立て・発送ができ、所持金が増える
   - アルバイトを雇える
   - 再読み込みしてもセーブが残る
3. 生産・制作・販売・雇うシート・夜の配色のスクリーンショットを docs/screens/ に保存し、docs/rough/ の画像と見比べて大きな崩れがないことを確認する
4. GitHub Actions で main への push ごとにテスト→ビルド→GitHub Pages へ公開され、https://109mei.github.io/pc-tycoon/ で遊べる
5. README.md に遊び方・開発の始め方・テストの回し方を書く
6. 報告には、5章の各指標の実測値（目安との比較）と、仕様からの変更点・迷った点を入れる
